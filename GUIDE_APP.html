Construis SnapNote
étape par étape.

Une application où l’on photographie un ticket de caisse : une IA lit les montants, la note est enregistrée, et le comptable la reçoit par email. Tu la construis avec Claude Code, une brique à la fois.

  • Dépôt + Vercel + CI
  • Starter

  • IA
  • n8n
  • Fusion

Le résultat que tu vas construire.

Avant de commencer

  • Installé sur ton poste : Node.js (version 24 recommandée), Git et Claude Code.
  • Comptes gratuits : GitHub, Supabase et Vercel. Pour l’envoi d’emails : un accès n8n et une adresse d’envoi (SMTP). La clé de l’IA s’obtient sur app.jedha.co.

Cinq règles pour toute la démo

  • Un seul objectif à la fois. Termine une étape et vérifie-la avant de passer à la suivante.
  • Ne partage jamais un secret avec l’IA. Le fichier .env reste sur ton ordinateur ; Claude n’a pas le droit de le lire.
  • Relis ce que l’IA a produit. Lance npm run build et teste à la main avant de dire « c’est fini ».
  • Commite et pousse à la fin de chaque étape. Ta pull request se met à jour et la CI doit rester verte.
  • Utilise des tickets fictifs. Pas de vraies données personnelles. Des exemples sont dans public/samples/.
1

Dépôt, déploiement, branche et CI

Ton projet vit sur GitHub et en ligne dès le départ. Tu travailles sur une branche, avec cinq contrôles automatiques et une adresse d’aperçu pour comparer ta version à celle de main.

À faire : mettre le starter sur GitHub

  1. Place le dossier du starter (fourni par ton formateur) où tu veux, puis ouvre un terminal dedans.
  2. Initialise Git et fais un premier commit : 
    git init -b main
git add -A
git commit -m "Ajout du starter SnapNote"
  3. Sur github.com, crée un dépôt vide : New repository, nom SnapNote, privé, et sans README, sans .gitignore, sans licence.
  4. Relie ton dossier à ce dépôt (c’est le remote, appelé origin) et envoie le code. Remplace TON_PSEUDO par ton identifiant GitHub : 
    git remote add origin https://github.com/TON_PSEUDO/SnapNote.git
git push -u origin main
  5. Contrôle que le lien est bien fait : 
    git remote -v
    Deux lignes origin (fetch et push) doivent s’afficher, et ton code doit apparaître sur GitHub.
Raccourci : avec la ligne de commande GitHub, gh repo create SnapNote --private --source=. --push fait les étapes 3 et 4 d’un coup (création du dépôt, ajout du remote et envoi).

À faire : déployer la version de base avec Vercel

  1. Sur vercel.com : Add New → Project, importe le dépôt SnapNote. Vercel reconnaît Vite tout seul : clique Deploy.
  2. Ouvre l’adresse obtenue : c’est la version de base, celle de main (l’environnement Production).
Ce que tu viens de mettre en place : chaque fois que tu pousses une branche, Vercel crée une adresse d’aperçu distincte. main reste intacte tant que tu ne fusionnes pas. Tu pourras donc comparer à tout moment la version en ligne (main) et la version sur laquelle tu travailles, avant la pull request.

À faire : créer ta branche de travail

  1. C’est sur cette branche que tu feras toute la démo ; main ne reçoit que du code vérifié : 
    git switch -c feature/snapnote

Demande à Claude : la CI

Lance Claude Code dans le dossier avec la commande claude, puis donne-lui cette demande :

Ajoute une CI GitHub Actions (.github/workflows/ci.yml) lancée sur chaque pull request et sur chaque push vers main, avec dans l’ordre : npm ci, npm run lint, npm run typecheck, npm test, npm run build. Installe et configure ESLint, la vérification de types sur le JavaScript (tsc) et Vitest, avec des tests sur les fonctions pures de src/lib. Les cinq commandes doivent passer en local avant que tu me dises que c’est fini.
CommandeCe qu’elle vérifie
npm ciL’installation propre des dépendances
npm run lintLe style et les erreurs probables
npm run typecheckLa cohérence des types
npm testLes calculs et les règles (montants, statuts…)
npm run buildL’application se compile

À faire : ouvrir une pull request et voir la CI travailler

  1. Commite et envoie ta branche : 
    git add -A
git commit -m "Ajout de la CI"
git push -u origin feature/snapnote
  2. Sur GitHub, ouvre une pull request de feature/snapnote vers main. Garde-la ouverte pendant toute la démo : chaque nouveau push la met à jour et relance les contrôles.
  3. Dans l’onglet Checks de la PR, attends la coche verte. Vercel ajoute aussi un lien d’aperçu de ta branche.
  4. Fais l’essai de l’échec : casse volontairement un test (change un montant attendu), pousse, observe la croix rouge et lis le journal de l’étape en échec. Corrige, pousse : le vert revient.
Pourquoi la CI sur la PR et sur main seulement ? Lancer la CI à chaque push de chaque branche la ferait tourner deux fois dès qu’une PR est ouverte. Pour empêcher une fusion en échec, active une « protection de branche » sur main (Settings → Branches) ; selon ton abonnement GitHub, elle n’est pas toujours disponible sur un dépôt privé.

Vérifie

Pièges :
• git push échoue avec « no upstream » ou « remote not found » : le remote n’est pas configuré. Relance git remote -v, et ajoute-le avec git remote add origin ….
• Si npm run lint, typecheck ou test n’existent pas, la CI échoue tout de suite : c’est pour cela que la demande ci-dessus les fait créer.
• Une branche sans pull request ouverte ne déclenche pas la CI (elle ne se lance que sur les PR et sur main), alors que l’aperçu Vercel, lui, est créé à chaque push de branche.

Découvrir le starter

Une application qui marche déjà en saisie manuelle, et un cadre qui guide l’IA.

À faire

  1. Dans le terminal, à la racine du projet : 
    npm install
npm run dev
  2. Ouvre l’adresse affichée dans le terminal (souvent http://localhost:5173).
  3. Clique sur Scanner un justificatif, choisis public/samples/ticket-restaurant.png, remplis les champs et enregistre. Recharge la page : la note disparaît, c’est normal, rien n’est encore sauvegardé.
  4. Lis les trois fichiers qui encadrent l’IA : prd.md (quoi construire), design.md (à quoi ça ressemble) et CLAUDE.md (les règles). Ouvre aussi design/maquette/index.html : c’est l’application terminée.

Demande à Claude

Lis prd.md, CLAUDE.md et design.md. Explique-moi en dix lignes la structure du projet et ce que fait chaque dossier.
Le « harness » : c’est le cadre donné à l’IA. Ici, CLAUDE.md fixe les règles et .claude/settings.json les permissions (par exemple : interdit de lire .env, confirmation avant un git push).

Vérifie

Piège : npm install doit être lancé à la racine du projet, là où se trouve package.json. Sinon : « package.json introuvable ».

Connexion des employés

Seuls les employés dont tu as créé le compte peuvent entrer. Pas d’inscription publique.

À faire dans Supabase

  1. Crée un projet : New project. Note le mot de passe de la base.
  2. Va dans Project Settings → API et copie l’URL du projet et la clé publishable.
  3. Copie .env.example vers .env et remplis : 
    VITE_SUPABASE_URL=https://xxxx.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_xxxx
  4. Ajoute aussi ces deux variables dans Vercel : Settings → Environment Variables, en laissant cochés Production et Preview. Le fichier .env n’est jamais déployé : sans elles, l’aperçu de ta branche afficherait « Configuration manquante ».
  5. Crée un employé : Authentication → Users → Add user → Create new user, avec un email, un mot de passe, et la case Auto Confirm User cochée.
  6. Interdis l’inscription publique : Authentication → Sign In / Providers, décoche Allow new users to sign up.

Demande à Claude

Lis prd.md (US3) et CLAUDE.md. Ajoute une page de connexion pour les employés avec Supabase (email + mot de passe). Il ne doit y avoir aucun lien ni bouton de création de compte. Utilise les variables VITE_SUPABASE_URL et VITE_SUPABASE_PUBLISHABLE_KEY (ne lis jamais le fichier .env). Sans session, affiche seulement la page de connexion ; avec une session, affiche l’app avec le nom de l’employé et un bouton de déconnexion. Traduis les erreurs en français. Si les variables manquent, affiche un message clair. Respecte design.md.

Vérifie

Piège : une variable lue par le navigateur doit commencer par VITE_. Et après chaque modification du .env, relance npm run dev.
Masquer le bouton « Créer un compte » ne suffit pas : c’est la case décochée dans Supabase qui protège vraiment.

Enregistrer les notes et les photos

Chaque note est sauvegardée avec son auteur et sa date. Un employé ne voit que ses notes.

Demande à Claude

Lis prd.md (US4 et le modèle de données §7). Crée un script SQL supabase/001_receipts.sql avec : la table receipts, la RLS (chaque employé ne lit, ajoute, modifie, supprime que ses notes), un trigger qui impose user_id, user_email et created_at côté base, et un bucket Storage privé « receipts » avec des règles par dossier d’employé. Ne l’exécute pas : je le collerai moi-même dans Supabase. Ensuite, branche l’app : les notes sont enregistrées dans Supabase, la photo dans le bucket, et affichée par une URL signée temporaire. Le navigateur n’envoie jamais user_id.

À faire dans Supabase

  1. Ouvre SQL Editor → New query, colle le contenu du fichier supabase/001_receipts.sql, clique Run.
  2. Contrôle : Table Editor montre la table receipts ; Storage montre le bucket receipts en privé.
  3. Crée un deuxième employé (comme à l’étape 2) pour tester l’isolation.

Vérifie

À retenir : la clé publishable est dans le code de l’application, donc visible de tous : n’importe qui peut l’utiliser pour interroger ta base. Le navigateur ne peut donc rien protéger lui-même. C’est la base de données qui le fait, avec la RLS (Row Level Security) : une règle qui dit « tu ne vois et ne modifies que les lignes où user_id est le tien ». Pour la même raison, c’est la base — et jamais le navigateur — qui écrit l’auteur de la note : sinon un employé pourrait signer à la place d’un autre.

Comment ça marche : la règle s’appelle une policy. C’est elle qui empêche un utilisateur de voir les notes des autres : à chaque requête, Supabase ajoute la condition user_id = auth.uid() (l’identifiant de la personne connectée). Camille demande « toutes les notes » et ne reçoit que les siennes ; même si quelqu’un modifie la requête dans son navigateur pour viser les notes d’un collègue, la base répond avec une liste vide.

Trois éléments fonctionnent ensemble : la RLS activée sur la table (sans elle, la policy est ignorée), la colonne user_id remplie par la base, et une policy par action (lire, ajouter, modifier, supprimer). Tout ce qu’aucune policy n’autorise est interdit.

Lecture automatique par l’IA

Tu prends la photo, l’IA remplit enseigne, date, HT, TVA, TTC et catégorie. Tu vérifies et tu enregistres.

À faire

  1. Récupère la clé et l’URL de l’API IA sur app.jedha.co, puis ajoute-les dans ton .env (sans préfixe VITE_ : elles ne doivent jamais arriver dans le navigateur) : 
    JEDHA_AI_API_KEY=...
JEDHA_AI_BASE_URL=...
  2. Ajoute-les aussi dans Vercel (Environment Variables, Production et Preview), puis redéploie. Elles restent secrètes : c’est le backend qui les lit.
  3. Donne la demande ci-dessous à Claude, puis relance npm run dev.

Demande à Claude

Lis prd.md (US5). Ajoute la lecture automatique des tickets par une IA de vision. L’appel à l’IA passe par un backend api/extract.js, jamais depuis le navigateur. Il utilise JEDHA_AI_API_KEY et JEDHA_AI_BASE_URL (API compatible OpenAI), modèle openai/gpt-4.1-mini, et refuse toute requête sans session Supabase valide. Valide et nettoie la réponse de l’IA (date réelle, montants positifs, catégorie de la liste) et signale les incohérences, par exemple HT + TVA différent du TTC. Réduis l’image avant l’envoi. Les champs sont pré-remplis mais restent modifiables, et si l’IA échoue la saisie manuelle reste possible. Ne lis jamais .env.

Vérifie

Piège : ne fais jamais confiance à la réponse d’une IA. Elle est lue, validée et contrôlée par le backend ; les incohérences sont signalées à l’employé, pas corrigées en silence.
À retenir : tout ce que le navigateur reçoit peut être lu par n’importe qui (onglet « Réseau » des outils du navigateur). Si l’application appelait l’IA directement, la clé secrète serait visible : quelqu’un pourrait la copier et consommer ton crédit. Le backend est la seule partie qui connaît la clé : le navigateur lui envoie la photo, il appelle l’IA, puis il renvoie seulement le résultat. Il vérifie aussi que l’employé est connecté, sinon n’importe qui pourrait l’utiliser.
6

Envoyer la note au comptable avec n8n

Dès qu’une note est enregistrée, le comptable reçoit un email avec le récapitulatif et la photo.

Le principe

Supabase (nouvelle note) → webhook → n8n → email au comptable → note marquée « envoyée »

L’application n’appelle jamais n8n : c’est la base de données qui le prévient. Moins de code, moins de pannes.

À faire dans n8n : importer le workflow fourni

Le workflow est déjà construit : c’est le fichier n8n/snapnote-workflow.json du starter. Tu l’importes, puis tu le configures. Il ne contient aucun secret : les identifiants se créent chez toi.

  1. Dans n8n : Create workflow, puis le menu ⋯ → Import from file, et choisis n8n/snapnote-workflow.json. Neuf nœuds apparaissent.
  2. Ouvre le nœud Configuration et remplace les trois valeurs :
    ChampValeur à mettre
    accountantEmailL’adresse du comptable (ou la tienne pour tester)
    fromEmailUne adresse d’expéditeur que ton compte SMTP a le droit d’utiliser
    supabaseUrlL’URL de ton projet Supabase (la même que VITE_SUPABASE_URL)
  3. Le secret du webhook (nœud Nouvelle note (Supabase)). Ce secret empêche n’importe qui de déclencher l’envoi d’emails : seul Supabase le connaîtra.
    1. Génère un secret aléatoire. Dans un terminal : 
      node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
      Copie le résultat (64 caractères) et garde-le dans un fichier à part : tu le recolleras dans Supabase plus bas.
    2. Double-clique sur le nœud Nouvelle note (Supabase). Dans le champ Credential for Header Auth, ouvre la liste et choisis Create new credential.
    3. Dans la fenêtre qui s’ouvre, remplis deux champs :
      ChampValeur
      Namex-snapnote-secret (c’est le nom de l’en-tête, à écrire exactement ainsi)
      ValueLe secret que tu viens de générer
    4. En haut de la fenêtre, clique sur le nom de l’identifiant et renomme-le en SnapNote - secret du webhook, puis clique Save.
    5. Dans le même nœud, ouvre l’onglet Production URL et copie l’adresse : c’est celle que tu donneras à Supabase. Pas celle de l’onglet Test URL.
  4. La clé secrète Supabase (nœuds Télécharger la photo et Marquer la note comme envoyée). Ces deux nœuds lisent et modifient la base sans passer par un employé : ils ont besoin de la clé secrète de ton projet.
    1. Dans Supabase : Project Settings → API Keys. Dans la section des clés secrètes (Secret keys), copie la clé qui commence par sb_secret_ (bouton pour la révéler, puis copier). Si ton projet n’affiche que d’anciennes clés, utilise la clé service_role.
    2. Double-clique sur le nœud Télécharger la photo. Vérifie que Authentication est sur Generic Credential Type et Generic Auth Type sur Header Auth. Dans Header Auth, ouvre la liste et choisis Create new credential.
    3. Remplis les deux champs :
      ChampValeur
      Nameapikey
      ValueLa clé sb_secret_… que tu viens de copier
    4. Renomme l’identifiant en SnapNote - clé secrète Supabase, puis Save.
    5. Ouvre le nœud Marquer la note comme envoyée et, dans Header Auth, sélectionne le même identifiant dans la liste (ne le recrée pas).
    Cette clé donne tous les droits sur ta base. Elle ne doit apparaître que dans n8n : jamais dans le code, jamais dans le .env de l’application, jamais dans un message à l’IA. À ne pas confondre avec la clé publishable, qui est celle de l’application.
  5. Nœuds Envoyer au comptable (il y en a deux : avec et sans photo) : choisis ou crée ton identifiant SMTP.
  6. Clique Publish pour activer le workflow.
Ce que fait le workflow : il reçoit la nouvelle note, prépare un email au design de l’application, télécharge la photo dans le Storage, envoie l’email avec la photo en pièce jointe (ou sans, s’il n’y en a pas), puis passe la note à status = sent. Ce dernier nœud est placé après l’envoi : si l’email échoue, la note reste en brouillon.

À faire dans Supabase

  1. Database → Webhooks → Create a new hook : table receipts, évènement Insert, méthode POST.
  2. URL : l’URL de production du webhook n8n (elle contient /webhook/, pas /webhook-test/).
  3. Ajoute l’en-tête x-snapnote-secret avec le même secret que dans n8n.

Dernier réglage : voir l’envoi en direct

Après l’enregistrement, la note doit afficher « Envoi en cours », puis passer toute seule à « Envoyée » sans recharger la page (Supabase Realtime). Si l’envoi n’est pas confirmé au bout de 2 minutes, elle devient « Non envoyée » et peut être supprimée. Une note envoyée ne peut plus être modifiée ni supprimée. Écris la migration SQL nécessaire.

Vérifie

Pièges :
• Après l’import, les identifiants sont vides : c’est normal et voulu. Un nœud qui affiche un identifiant manquant n’a pas encore le sien.
• Un workflow non publié ou une URL webhook-test ne déclenche rien.
• Si le serveur SMTP refuse l’expéditeur (erreur 553), la note reste en brouillon : c’est voulu. Le statut « envoyée » n’est écrit qu’après un envoi réussi.
• Pour comprendre une panne : n8n → Executions → ouvre l’exécution, le nœud en rouge donne le message exact.
7

Fusionner et mettre en ligne

Tu compares la version de ta branche à celle de main, puis tu fusionnes : la version testée devient la version en ligne.

À faire

  1. Ouvre côte à côte l’adresse de main (version de base) et l’aperçu Vercel de ta branche : tu dois voir la différence (connexion, lecture par l’IA, notes enregistrées).
  2. Dans Supabase : Authentication → URL Configuration, mets l’adresse de production dans Site URL.
  3. Teste l’aperçu sur ton téléphone (Safari ou Chrome) : connecte-toi et scanne un ticket fictif.
  4. Vérifie que la CI de ta pull request est verte, puis fusionne la PR dans main.
  5. Vercel publie automatiquement la nouvelle version de main. Ouvre l’adresse de production et refais un test complet.

Vérifie

Pièges :
• Les variables VITE_* sont lues à la construction de l’application : si tu en modifies une, il faut redéployer.
• La caméra exige le HTTPS (fourni par Vercel). Sur iPhone, ouvre le lien dans Safari, pas dans le navigateur intégré d’une autre application.
• Rien à configurer côté Vercel pour n8n : c’est Supabase qui l’appelle, directement.

Ce que tu as construit

Un employé se connecte, photographie un ticket, l’IA lit les montants, il vérifie, enregistre, et le comptable reçoit l’email avec la photo. Chaque scan est rattaché à son auteur, le code est contrôlé automatiquement, et l’application est en ligne.

Guide SnapNote — à utiliser avec des tickets fictifs uniquement.
